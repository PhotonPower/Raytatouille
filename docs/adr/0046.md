# ADR 0046: Komplexe Wurzel ohne Abhängigkeit von der Standardbibliothek

**Status:** angenommen (Maintainer, 2026-11-11, #373)

## Kontext

`rtt-polar` (`normal_component` in `fresnel.hpp`) und `rtt-coating` (`normal_component` in
`transfer_matrix.hpp`) berechnen die Normalkomponente q = n cos θ = √(n² − ξ²) mit
`std::sqrt(std::complex<double>)`. Bei Totalreflexion ist n² − ξ² eine negative reelle Zahl,
also muss q rein imaginär sein: Re q = 0.

Der C++-Standard schreibt für `std::sqrt` von `std::complex` keinen Rechenweg vor. Die
Standardbibliotheken weichen deshalb in den letzten Bits ab. Ein Testbuild auf macOS 26 (#373)
zeigt das:

| Bibliothek | `sqrt(-0.5 + 0i)` |
| --- | --- |
| libstdc++ (GCC), MSVC | Re = 0 (nicht einzeln gemessen; belegt dadurch, dass die Tests mit `tir.real() == 0.0` in `test_fresnel.cpp` dort in der CI grün sind) |
| libc++ (Apple clang 21, macOS 26.4, gemessen) | `4.33e-17 + 0.70710678118654757i` |

libc++ rechnet über die Polarform, also mit √|z| · cos(π/2) ≠ 0. Das ist mehr als ein
Rundungsfehler: `IdealCoating::amplitudes` (`rtt-coating/src/ideal.cpp`) erkennt die
Totalreflexion an `!(Re q > 0)`. Mit Re q = 4·10⁻¹⁷ gilt die Totalreflexion nicht als erkannt,
und die ideale Beschichtung lässt Licht durch, wo keines durchkommen darf (Test
`ideal coating under total internal reflection …`: r_s = −0,0 statt −0,118). Dazu kommen
Transmissionsgrade von 6·10⁻¹⁷ statt 0 in `fresnel_power` und im Schichtstapel. Auf macOS
waren 7 Tests rot.

ADR 0011 garantiert Bitgleichheit nur je Plattform und Compiler. Die Fallunterscheidung
„Totalreflexion ja/nein“ darf aber nicht von der Standardbibliothek abhängen.

## Entscheidung

1. **Eigene Funktion `rtt::math::principal_sqrt`** in `rtt-math` (`rtt/math/complex.hpp`),
   Template über `math::Real` (ADR 0006). Sie rechnet den Hauptwert in kartesischer Form nach
   Abramowitz & Stegun, Gl. 3.7.3 und 3.7.27:
   - r = |z| = (x² + y²)^½, berechnet mit `hypot`;
   - √z = u + iv mit u = [½(r + x)]^½, |v| = [½(r − x)]^½, 2uv = y, und v hat das Vorzeichen von y;
   - Hauptwert für −π < arg z ≤ π.
2. **Nur die Komponente ohne Auslöschung kommt aus einer Wurzel**, die andere aus 2uv = y:
   - für x ≥ 0: u = √(r/2 + x/2), v = y/(2u);
   - für x < 0: v = ±√(r/2 − x/2), u = |y|/(2v).

   Für eine negative reelle Zahl (y = +0) ist damit u = 0 exakt und v = √|x| korrekt
   gerundet. Die Hälften werden vor der Summe gebildet, damit r + |x| nahe der größten
   `double` nicht überläuft.
3. **Vorzeichen der Null wie `csqrt` in C11** (N1570, §7.3.8.3 und §G.6.4.2):
   csqrt(conj z) = conj csqrt(z) und csqrt(±0 + i0) = +0 + i0. y = −0 ist also die untere
   Seite des Schnitts. `normal_component` in `rtt-polar` setzt −0 weiterhin vorher auf +0, wie
   bisher.
4. **Beide Aufrufstellen nutzen `math::principal_sqrt`.** Der Zweig nach Byrnes, App. D
   (Im q ≥ 0, bei Im q = 0 auch Re q ≥ 0), bleibt unverändert dahinter.
5. **Neue komplexe Wurzeln im Physikcode** nutzen ebenfalls `math::principal_sqrt`, nicht
   `std::sqrt`. Reelle Wurzeln bleiben `std::sqrt`; IEEE 754 schreibt sie korrekt gerundet vor.

## Folgen

- Unter Linux und Windows kann sich q in den letzten Bits ändern: `principal_sqrt` hat einige ulp
  Fehler je Komponente, glibc und MSVC sind teils genauer. ADR 0011 garantiert Bitgleichheit nur
  je Plattform. C++ und Python nutzen denselben Header, also bleiben die Bitvergleiche gleich.
- Auf macOS sind die 7 Tests zur Totalreflexion grün, ohne geänderte Toleranzen.
- Der Test `rtt-math/tests/test_complex.cpp` prüft bitgenau: negative und positive reelle Zahlen,
  Pythagoras-Quadrate wie (3 + 4i)² = −7 + 24i, Vorzeichen der Null nach C11; außerdem
  q² ≈ z auf 8 ε |z|.

## Verworfen

- **`std::sqrt` behalten und die Tests lockern:** Das verdeckt einen echten Fehler. Die
  Fallunterscheidung in `ideal.cpp` bliebe falsch.
- **Re q nach der Wurzel auf 0 setzen, wenn |Re q| klein ist:** Das braucht eine willkürliche
  Schwelle und stimmt bei schwach absorbierenden Medien nicht mehr, denn dort ist Re q klein,
  aber echt.
- **`csqrt` aus `<complex.h>` von C:** Es ist in C++ nicht portabel verfügbar (MSVC hat
  `_Dcomplex` statt `double _Complex`), und der Rechenweg bliebe Sache der Bibliothek.
