# ADR 0029: Parametertabelle und Konfigurationen

**Status:** angenommen (2026-10-09)

## Kontext

M5 bringt die Optimierung (Roadmap in `docs/architecture.md`: „Parameter-Pfade, Operanden, Merit-Generatoren, LM, Grenzen, Pickups, Konfigurationen“). Abgestimmt sind die Entscheidungen F1–F9 und G1–G4 des Planentwurfs (#160, mit dem Maintainer am 2026-10-09). Das Vorbild für die Parametertabelle ist QUADOA (Handbuch V 24.08, Kap. 16). Es dient nur als Vorbild; aus dem Handbuch steht nichts im Repo außer diesem Verweis.

**Ist-Stand (`main` nach 0.6.0, Schema 0.3.0):**
- Jeder optimierbare Wert ist ein `Param { double value; bool variable; std::optional<std::string> pickup; }` (`rtt/model/param.hpp`). Params sind:
  - die Radien, Konik und Koeffizienten der Formen;
  - `lines_per_mm` und die Koeffizienten der Phasenschichten;
  - Ort und Drehung jeder Pose;
  - der Wert der Systemapertur;
  - der Objektabstand.
  
  Wellenlängen, Feldpunkte, Materialien und Pfade sind keine Params.
- `pickup` ist ein freier String, den nichts auswertet. Seine Syntax ist nie festgelegt worden. compile ignoriert ihn (Test „pickups are not evaluated“ in `test_compile.cpp`). Die Feature-Tour zeigt ihn mit `{"value": 6.0, "pickup": "2 * 3"}`.
- ADR 0024, Punkt 2 sieht für Pickups verankerte Verweise vor (Anker Fläche/Knoten/Pfad plus angehängter Pointer) und überlässt ihre Textsyntax einem M5-ADR. Offen blieb dort, wie man Wellenlängen und Feldpunkte ohne Namen dauerhaft adressiert.
- Die Bearbeitungsform schreibt jedes Param als Objekt `{"value": …, "variable": …}`, `pickup` nur, wenn er gesetzt ist. Darum ist `…/value` heute immer adressierbar.
- Konfigurationen gibt es nicht. Ein Zoom oder ein umschaltbares System braucht heute je Stellung eine eigene Datei.
- Relative Platzierung (ADR 0028, #159) macht eine Luftdicke zu **einem** Param, weil die Folgeelemente mitwandern. Das ist die Voraussetzung, damit eine Tabellenzeile „Luftabstand“ sinnvoll ist.

## Entscheidung

### 1. Format: Konfigurationen und Parametertabelle

Zwei neue Abschnitte auf oberster Ebene der Systemdatei (Schema 0.4.0, ein gemeinsamer Sprung mit ADR 0028 und ADR 0030 in #162):

```json
"configurations": [{"name": "wide"}, {"name": "tele"}],
"parameters": [
  {"name": "TOTAL", "value": 40.0},
  {"name": "G", "values": [20.0, 5.0], "variable": true, "min": 2.0, "max": 30.0},
  {"name": "B", "expression": "TOTAL - G"}
]
```

- **`configurations`:** Liste von Objekten mit `name`. Fehlt der Abschnitt, gibt es genau **eine** Konfiguration, die Nominalkonfiguration (Index 0, ohne Namen). Ein vorhandener Abschnitt ist nicht leer; eine leere Liste ist ein Lesefehler. Die Anzahl der Konfigurationen heißt im Folgenden C (≥ 1).
  - Objekte statt bloßer Strings, damit spätere Angaben je Konfiguration (z. B. ein Gewicht in der Merit-Funktion, ADR 0030) verträglich dazukommen.
- **`parameters`:** Liste von Zeilen in fester Reihenfolge. Jede Zeile hat einen `name` und **genau eine** der drei Formen:
  - `value` (Zahl): unabhängig, derselbe Wert in allen Konfigurationen;
  - `values` (Array mit genau C Zahlen): unabhängig, ein Wert je Konfiguration, in der Reihenfolge von `configurations`;
  - `expression` (String): abgeleitet, je Konfiguration aus früheren Zeilen berechnet (Punkt 2).
  
  Dazu kommen optional:
  - `variable` (Bool, Standard `false`) an jeder Zeile; `true` an einer abgeleiteten Zeile ist ein validate-Fehler (Punkt 5);
  - `min` und `max` (Zahlen, beide optional) nur an unabhängigen Zeilen. An einer abgeleiteten Zeile sind sie ein Lesefehler (unbekannter Schlüssel).
  
  Keine oder mehrere der drei Formen sind ein Lesefehler.
- **Namen** von Zeilen folgen `[A-Za-z_][A-Za-z0-9_]*` (ASCII) und sind eindeutig. Groß- und Kleinschreibung zählen, wie überall im Modell.
  - Namen von Konfigurationen sind nicht leer, nicht nur Leerraum und eindeutig. Sie erscheinen nie in Ausdrücken.
  - Beide Namensräume sind getrennt von denen der Flächen, Knoten und Pfade (ADR 0024, Punkt 2).
- **Kanonisch** (ADR 0008, 0024) fehlen leere Abschnitte, `"variable": false` und nicht gesetzte Grenzen. Die beiden Abschnitte stehen vor `root`, damit ein Leser die Tabelle vor ihren Verwendungen sieht.

### 2. Ausdrücke

```text
expression = term { ("+" | "-") term } ;
term       = factor { ("*" | "/") factor } ;
factor     = "-" factor | primary ;
primary    = number | name | "(" expression ")" ;
number     = int [ "." digit { digit } ] [ ("e" | "E") [ "+" | "-" ] digit { digit } ] ;
int        = "0" | nonzero { digit } ;
name       = ( letter | "_" ) { letter | digit | "_" } ;
digit      = "0" | nonzero ;
nonzero    = "1" | "2" | "3" | "4" | "5" | "6" | "7" | "8" | "9" ;
letter     = "A" | … | "Z" | "a" | … | "z" ;   (* ASCII only *)
```

- Leerzeichen und Tabulatoren zwischen den Token sind erlaubt.
- Eine Zahl hat genau die Form einer JSON-Zahl ohne Vorzeichen (RFC 8259, Abschnitt 6): keine führende Null vor weiteren Ziffern, kein `.5` und kein `1.`. Ein Vorzeichen ist immer das unäre Minus.
- **Literale werden korrekt gerundet und unabhängig von der Locale gelesen:** mit `std::from_chars` für `double` (Rundung zum nächsten, bei Gleichstand zur geraden Mantisse), nicht mit `strtod` oder `std::stod`. Der Abnahmefall in #164 enthält ein Literal genau in der Mitte zwischen zwei benachbarten doubles.
- Ein unäres Plus gibt es nicht.
- **Keine Funktionen**, solange kein Abnahmefall sie braucht. Kommen später Funktionen (`sqrt(…)`), erkennt der Parser sie nur mit folgender Klammer. Ein Zeilenname kann nie vor `(` stehen; Zeilen namens `sqrt` bleiben also gültig. Benannte Konstanten wie `pi` kommen nicht als bloßer Name, denn sie könnten mit einer Zeile kollidieren.
- **Nur frühere Zeilen:** Ein Name muss eine Zeile **vor** der aktuellen bezeichnen. Ein späterer Name oder die Zeile selbst ist `parameters.forward_reference`. Damit gibt es keine Zyklen und keine Sortierung; die Tabelle wird in Dateireihenfolge ausgewertet.
- **Auswertung** je Konfiguration in Tabellenreihenfolge, in `double`, als Baum genau nach der Grammatik:
  - Operatoren sind linksassoziativ: `a - b - c` = `(a - b) - c`.
  - Das unäre Minus ist die exakte Negation.
  - Es gibt keine Umordnung und kein Zusammenfassen von Konstanten. Der Auswerter steht in einer eigenen Übersetzungseinheit, die ohne FMA-Kontraktion übersetzt wird (GCC und Clang mit `-ffp-contract=off`, MSVC ohne `/fp:contract`). Eine eigene Übersetzungseinheit, weil die Rechenoperationen sonst in Aufrufer mit anderen Optionen eingebettet (inlined) werden könnten. Dasselbe Ergebnis auf allen Plattformen ist Teil der Abnahme (#164).
  - Python ruft denselben Auswerter auf und ist dadurch bitgleich.
- **Nicht endlich** (Division durch null, Überlauf) ist `parameters.not_finite` am Ausdruck, mit dem Namen der Konfiguration in der Meldung. Nicht endliche Eingabewerte (`value`, `values`, über die API) meldet `value.not_finite`.
- **Grenzen gegen Missbrauch:** höchstens 1000 Zeichen und eine Schachtelungstiefe von 64. Die Tiefe zählt **jede** Schachtelung von `factor`, also jede öffnende Klammer und jedes unäre Minus; `--------x` mit 65 Minuszeichen ist ebenso zu tief wie 65 Klammern. Mehr ist `parameters.expression_syntax`. Der Parser rekursiert nie tiefer und wirft keine Exception (AGENTS.md, Regel 3); Fehler sind Diagnosen. #164 prüft beide Grenzfälle (64 und 65 Minuszeichen, 64 und 65 Klammern).
- Ausdrücke gibt es nur in Tabellenzeilen. Ein Modell-Param bindet an eine Zeile (Punkt 3), trägt aber selbst keinen Ausdruck. Für „R2 = −R1“ legt man eine abgeleitete Zeile an.

### 3. Modell-Param verweist auf eine Zeile

- **Datei:** Ein Param hat jetzt drei Formen:
  - eine Zahl;
  - ein Objekt `{"value": n, "variable": b, "min": n, "max": n}` (nur `value` ist Pflicht);
  - ein Verweis `{"param": "NAME"}`.
  
  Der Verweis trägt **keinen eigenen Wert**. Weitere Schlüssel neben `param` sind ein Lesefehler.
- **C++** (`rtt/model/param.hpp`):

  ```cpp
  struct Param {
    double value = 0.0;                 // unbound: the value; bound: set by resolve_parameters
    bool variable = false;              // unbound only
    std::optional<double> min, max;     // unbound only (bounds for the optimizer)
    std::optional<std::string> param;   // name of a parameter row; replaces pickup
    Param(double v);                    // stays implicit
    [[nodiscard]] bool is_plain() const noexcept;  // !variable && !min && !max && !param
  };
  ```

  - Ein gebundener Param (`param` gesetzt) hat weder `variable` noch Grenzen. Das wird über die C++- und Python-API erreichbar und meldet `param.bound_conflict`; aus einer Datei kommt es nicht.
  - Sein `value` ist vor der Auswertung bedeutungslos (der Leser setzt 0). validate und die Writer lesen ihn nicht.
- **`resolve_parameters(system, configuration)`** (rtt-model) liefert eine Kopie des Systems:
  - Jeder gebundene Param wird durch einen ungebundenen Param mit dem ausgewerteten Wert ersetzt (`variable` false, keine Grenzen, `param` leer).
  - Tabelle und Konfigurationen bleiben unverändert in der Kopie stehen.
  - Das Ergebnis ist ein gewöhnliches System dieser Konfiguration: Gespeichert ist es eine Datei mit festen Zahlen („Konfiguration k exportieren“).
  - Bei einem ungültigen Index oder einer Tabelle mit Fehlern wirft die Funktion `std::invalid_argument` (API-Grenze, ADR 0009).
- **compile** ruft `resolve_parameters` **immer** auf, vor dem Zusammensetzen der Posen (#165). Vorher läuft wie heute `validate`: Fehler in der Tabelle kommen deshalb als `CompileError` mit ihren Diagnosen aus compile, nie als `std::invalid_argument`. Ohne Tabelle und ohne gebundene Param ist die Kopie gleich dem Eingabesystem, und das Ergebnis bleibt bitgleich.
- **Bearbeitungsform** (ADR 0024, Punkt 3):
  - Gebundene Params stehen dort ebenfalls als `{"param": …}`.
  - Ungebundene Params stehen als Objekt mit `value` und `variable`, dazu `min`/`max`, wenn gesetzt.
  - Tabellenzeilen stehen mit allen Schlüsseln ihrer Form, an jeder Zeile mit `variable` (an abgeleiteten Zeilen `false`). So ist `/parameters/i/variable` immer adressierbar, wie ein GUI-Schalter „variabel“ es braucht.
  - **Präzisierung von ADR 0024:** `…/value` ist nur an ungebundenen Params immer adressierbar. Eine GUI prüft `param`, bevor sie `value` ändert. Binden und Lösen heißt, das ganze Param-Objekt zu ersetzen (`replace` auf `…/radius`).
- **Python** (`raytatouille.model`):
  - `Param.value` ist bei einem gebundenen Param `None`, `Param.param` trägt den Namen.
  - `System.parameters` (Zeilen als unveränderliche Kopien) und `System.configurations` (Objekte `Configuration` mit `name`, wie in der Datei; präzisiert in #164) sind lesbar.
  - Ausgewertete Werte liefert `System.resolved(configuration)` mit `configuration` als Index oder Name; das ist dieselbe Funktion wie in C++.
  - `System.locate_parameter(name)` gibt den Pointer der Zeile zurück, wie `locate_surface`.

### 4. Variablen und Grenzen

- **Unbekannte** der Optimierung (Variante A, G2):
  - Eine variable Zeile mit `value` ist **eine** gemeinsame Unbekannte für alle Konfigurationen.
  - Eine variable Zeile mit `values` hat **C** Unbekannte, eine je Konfiguration.
  - Jeder ungebundene Modell-Param mit `variable` ist eine Unbekannte. Er hat in allen Konfigurationen denselben Wert, denn Konfigurationen ändern nur Tabellenwerte.
  - Abgeleitete Zeilen sind nie variabel. Sie folgen ihren Eingängen.
  
  Die Reihenfolge des Variablenvektors und die Ergebnis-Patches legt ADR 0030 (#161) fest. Ein Patch des Optimierers ersetzt `/parameters/i/value`, `/parameters/i/values/k` oder `…/value` eines Params.
- **Erweiterungspunkt:** Ein Flag je Zelle (QUADOA) kann später verträglich als Array `"variable": [true, false, …]` an einer `values`-Zeile kommen. Heute ist `variable` dort ein Bool.
- **Grenzen** `min`/`max` (F5) stehen an ungebundenen Modell-Params und an unabhängigen Zeilen. Bei `values` gelten sie für jede Konfiguration.
  - `min` < `max`, sonst `bounds.invalid`.
  - Ein Wert außerhalb ist `bounds.value_outside` (Warnung, denn eine Datei darf einen Startwert außerhalb haben).
  - Grenzen an nicht variablen Werten sind erlaubt und wirkungslos.
  - Wie der Optimierer Grenzen einhält, regelt ADR 0030.
- **Variablen im Modell finden** (F1): `for_each_param(system, visitor)` in rtt-model ruft den Besucher für jedes Param mit seinem Pointer in die Bearbeitungsform auf (const und nicht const). Die Pointer bildet rtt-model als Text, ohne JSON zu kennen.
  - Ein Wächtertest in `libs/rtt-io/tests` (#164) vergleicht die Pointer-Menge mit allen Param-Objekten in `to_edit_json` für alle Referenzsysteme und die Feature-Tour. Ein neues Param-Feld ohne Besuch fällt so auf.

### 5. Konfigurationen sind Spalten, nur für Parameter

- Konfigurationen ändern **nur** Werte, die über die Tabelle laufen (F4). Wellenlängen, Feldpunkte, Materialien, Pfade, Flächenarten und der Baum sind in allen Konfigurationen gleich. Auch Bezug, Reihenfolge und Pivot einer Pose (ADR 0028) sind keine Params und damit in allen Konfigurationen gleich.
  - Was je Konfiguration variieren soll, muss ein Param sein und an eine `values`-Zeile (oder eine davon abgeleitete Zeile) gebunden werden: Posen (Zoom), Radien, die Systemapertur oder der Objektabstand.
- **`compile(system, materials, coatings, configuration = 0)`** übersetzt genau eine Spalte.
  - Ein Index ≥ C ist `config.unknown` (CompileError mit Ort `/configurations` bzw. `""`, wenn der Abschnitt fehlt).
  - Das `CompiledSystem` merkt sich Index und Namen seiner Konfiguration, damit Ergebnisse und Merit-Funktionen sie nennen können.
  - Python nimmt `configuration=` als Index oder Name.
- **validate** wertet die Tabelle für **alle** Konfigurationen aus. `parameters.not_finite` in nur einer Spalte fällt also auf, auch wenn man eine andere kompiliert.
- **Diagnosecodes** (ADR 0022). Fehler, wenn nicht anders angegeben; der Pointer folgt jeweils dem Code:

  | Code | Pointer |
  | --- | --- |
  | `parameters.name_invalid`, `parameters.name_duplicate` (zweites Vorkommen) | `/parameters/i/name` |
  | `parameters.expression_syntax` (mit Zeichenposition), `parameters.unknown_name`, `parameters.forward_reference` | `/parameters/i/expression` |
  | `parameters.values_count` | `/parameters/i/values` |
  | `parameters.not_finite` (Ergebnis eines Ausdrucks, je Konfiguration) | `/parameters/i/expression` |
  | `parameters.variable_expression` | `/parameters/i/variable` |
  | `param.unknown_parameter` | `…/param` des Params |
  | `param.bound_conflict` (nur über die API erreichbar) | Param |
  | `bounds.invalid` | `…/min` |
  | `bounds.value_outside` (Warnung) | `…/value` bzw. `…/values/k` |
  | `configurations.name_invalid`, `configurations.name_duplicate` | `/configurations/k/name` |
  | `value.not_finite` für jede Zahl des Modells (Restpunkt aus #35/#127; die Datei lässt nicht endliche Zahlen schon heute nicht zu, die API schon) | Zahl |
  | `config.unknown` (compile) | siehe oben |

### 6. `pickup` entfällt (G3)

- Die Migration 0.3 → 0.4 lässt `pickup` fallen und behält `value`. Die alten Pickups wurden nie ausgewertet und hatten keine Syntax; eine automatische Übersetzung in Tabellenzeilen wäre geraten.
- Der Leser meldet jede verworfene Angabe als Warnung `io.pickup_dropped`:
  - Pointer auf `…/pickup` in der gelesenen Datei, der verworfene Text in der Meldung;
  - über einen **neuen Warnkanal des Lesers** in rtt-io (Diagnosen nach ADR 0022 mit Schweregrad Warnung, die Form der API legt #162 fest);
  - Python gibt sie beim Laden als `RaytatouilleWarning` aus.
- In einer 0.4-Datei ist `pickup` ein Lesefehler (unbekannter Schlüssel).
- Ein Changelog-Eintrag nennt den Wegfall. Die Feature-Tour zeigt danach eine Tabellenzeile statt des Pickups (Freigabe nach Regel 2 erteilt; die Testliste steht im Format-PR #162).

### 7. Verhältnis zu ADR 0024

ADR 0024 bleibt unverändert; dieses ADR löst einen Teil von Punkt 2 ab:
- Die **verankerten Pickup-Verweise** und ihre offene **Textsyntax** entfallen. Die Tabelle braucht keine Pointer in Ausdrücken: Ein Modell-Param zeigt mit `{"param": …}` auf eine Zeile, und Ausdrücke kennen nur Zeilennamen.
- **Zeilennamen sind selbst stabile Anker.** Gespeicherte Verweise auf Zeilen (z. B. Variablenlisten in `optimization`, ADR 0030) verwenden den Namen.
- Die offene Frage nach Ankern für Wellenlängen und Feldpunkte stellt sich für Pickups nicht mehr. Sie bleibt nur für Operanden offen (ADR 0030).
- Umbenennen pflanzt sich wie bei Flächen-IDs nicht fort: Eine umbenannte Zeile lässt `param.unknown_parameter` bzw. `parameters.unknown_name` entstehen. Die GUI packt die Folgeänderungen in denselben Patch.
- Dasselbe gilt für eine neue oder gelöschte Konfiguration: Alle `values`-Zeilen brauchen dann einen Eintrag mehr bzw. weniger (`parameters.values_count`).
- Undo über inverse Patches gilt unverändert.

### 8. Beispiel: Zoom mit zwei Konfigurationen und einer abgeleiteten Zeile

Zwei Linsen L1 und L2 und eine Bildfläche. Mit relativer Platzierung (ADR 0028) steht L2 im Abstand G hinter dem Scheitel von L1.S2 und die Bildfläche im Abstand B hinter dem letzten Scheitel von L2. Die Summe der beiden Luftabstände ist fest 40 mm. G ist je Stellung variabel, B folgt.

```json
"configurations": [{"name": "wide"}, {"name": "tele"}],
"parameters": [
  {"name": "TOTAL", "value": 40.0},
  {"name": "G", "values": [20.0, 5.0], "variable": true, "min": 2.0, "max": 30.0},
  {"name": "B", "expression": "TOTAL - G"}
],
"root": {"type": "assembly", "name": "zoom", "children": [
  {"type": "lens", "name": "L1", "...": "..."},
  {"type": "lens", "name": "L2",
   "pose": {"reference": "relative_to_preceding", "position": [0.0, 0.0, {"param": "G"}]},
   "...": "..."},
  {"type": "detector", "name": "image",
   "pose": {"reference": "relative_to_preceding", "position": [0.0, 0.0, {"param": "B"}]},
   "surfaces": [{"id": "IMG"}]}
]}
```

| Zeile | `wide` | `tele` | Art |
| --- | --- | --- | --- |
| `TOTAL` | 40 | 40 | unabhängig, fest |
| `G` | 20 | 5 | unabhängig, variabel: 2 Unbekannte (je Konfiguration eine), Grenzen 2 … 30 |
| `B` | 20 | 35 | abgeleitet: `TOTAL - G` |

- `compile(system, lib, coatings, 1)` übersetzt die Stellung `tele`. Das Ergebnis ist bitgleich zu dem System, in dem man G = 5 und B = 35 von Hand eingetragen hat (Abnahme in #165).
- Ändert der Optimierer `/parameters/1/values/1` um ΔG, wandern L2 um ΔG und die Bildfläche um null: Der Abstand B schrumpft um ΔG.

## Verworfen

- **Ausdrücke direkt am Modell-Param** (`"radius": "=-R1"` oder `{"value": …, "expression": …}`): Das wären zwei Orte für dieselbe Sache, und die Abhängigkeiten stünden verstreut im Baum. Eine abgeleitete Zeile kostet eine Zeile mehr, hält aber alle Rechnungen an einem Ort und in einer Reihenfolge.
- **Pickups mit Wert** (`{"param": "D1", "value": 5.0}` als Zwischenspeicher): Der Wert würde veralten, sobald sich die Zeile ändert, und es gäbe zwei Wahrheiten. Ausgewertete Werte liefert `resolved`.
- **Beliebige Reihenfolge mit topologischer Sortierung:** Das erlaubt Vorwärtsverweise, braucht aber Zykluserkennung und macht die Auswertungsreihenfolge unsichtbar. Die Tabellenreihenfolge ist sichtbar und reicht.
- **Konfigurationen für beliebige Felder** (Multi-Konfigurations-Editor mit Operanden je Feld, z. B. Wellenlängen oder Materialien je Stellung): Das ist mächtiger, aber F4 beschränkt Konfigurationen auf Parameter. Wellenlängen und Felder je Konfiguration wären ein späteres ADR mit eigenem Format.
- **Flag je Zelle schon jetzt:** Heute gibt es keinen Abnahmefall dafür. Das Format lässt es verträglich zu (Punkt 4).
- **Funktionen und Konstanten jetzt** (`sqrt`, `sin`, `pi`): Ohne Abnahmefall nicht nötig; der Weg für Funktionen ist offen (Punkt 2).
- **NaN als Platzhalter für den Wert gebundener Params:** Das kollidiert mit `value.not_finite` und mit bitweisen Vergleichen von Systemen. Der Wert ist stattdessen bis zur Auswertung bedeutungslos und wird nie geschrieben.
- **`pickup` automatisch in Tabellenzeilen übersetzen:** Es gab keine Syntax; Texte wie `2 * 3` ließen sich übersetzen, Verweise auf andere Werte nicht. Eine halbe Übersetzung wäre schlimmer als ein klarer Wegfall mit Warnung.

## Folgen

- **#162 (Format 0.4.0):**
  - Modell: `Param`, `ParameterRow`, `Configuration`, `System::parameters`/`configurations`.
  - Leser und Schreiber (kanonisch und Bearbeitungsform), JSON-Schema, Migration mit `io.pickup_dropped`, Warnkanal des Lesers.
  - Die validate-Codes ohne Auswertung (Namen, Anzahl der Werte, Grenzen, `param.bound_conflict`, `value.not_finite`).
  - Python-Lesetypen, Referenzdateien mit `rtt format`, Feature-Tour.
  - Regel-2-Liste im PR, u. a. „pickups are not evaluated“ in `test_compile.cpp`, `test_roundtrip.cpp`, `test_edit.cpp`, `test_editor.py`.
  - Changelog: Der Wegfall des öffentlichen Felds `Param::pickup` in C++ und `Param.pickup` in Python ist ein Eintrag „Entfernt“ im Fragment (`changelog.d/162.removed.md`), neben dem Wegfall von `pickup` im Dateiformat.
- **#164 (rtt-model):** Parser und Auswerter (eigene Übersetzungseinheit ohne FMA-Kontraktion), `resolve_parameters`, die auswertenden validate-Codes, `for_each_param` mit Wächtertest. Referenzfälle mit analytischen Werten je Konfiguration.
- **#165 (rtt-compile):** `compile(…, configuration)`, `config.unknown`. Nominalkonfiguration bitgleich wie ohne Tabelle; Spalte k gleich dem System mit Handwerten.
- **#169 (rtt-py):** `rt.compile(…, configuration=)`, `System.resolved`, `locate_parameter`.
- **ADR 0030 (#161):** Variablenvektor, Patches und Merit-Funktion über Konfigurationen bauen auf Punkt 4 und 5 auf.
- **`docs/architecture.md`:** Der Absatz „Parameter“ beschreibt nach #162 die Tabelle statt `pickup`. Die Roadmap-Zeile M5 nennt „Parametertabelle“ statt „Pickups“.
