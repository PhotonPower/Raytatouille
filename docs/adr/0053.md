# ADR 0053: Konstruktionshelfer singlet, doublet, triplet und Linsenkataloge als eigene JSON-Dateien

**Status:** angenommen (Maintainer, 2026-11-21; Entscheidungen in #321, auch zu den Fragen in Punkt 8: alle wie vorgeschlagen)

## Kontext

#321 (F5 aus P4, M8) verlangt Konstruktionshelfer `singlet`, `doublet` und `triplet` in Python und ein JSON-Format für Linsenkataloge samt Loader, ohne Herstellerdaten. Abnahme aus der Roadmap: `doublet(...)` ist bitgleich zu `tests/reference/m2/achromat.rtt.json`.

Stand:
- **Systeme entstehen heute nur aus Text.** Ein `rt.System` entsteht aus einer Datei (`rt.load`), aus JSON-Text (`System.from_json`) oder durch Patches an einem vorhandenen System (`rt.apply_patch`, `rt.Editor`). Einen Baukasten für Startsysteme gibt es nicht.
- **Die Referenzsysteme folgen einem Muster.** `m1/singlet_const`, `m2/achromat` und `m2/cooke_triplet_surface_stop` bestehen aus:
  - einer Blende (Knoten `stop` mit Fläche `STO`) oder einer Blendenfläche (`aperture.stop`, ADR 0039);
  - Linsen `L1`, `L2`, … mit den Flächen `L<i>.S<j>`, Lage des Knotens absolut, Lage der Flächen relativ zum Knoten (die Dicken);
  - einem Detektor `image` mit der Fläche `IMG`;
  - Systemdaten: Name, EPD, Wellenlängen mit Referenz, Felder in Grad, ein Pfad `main` mit `events: auto`.
  Plane Flächen haben keine `shape`.
- **Vorbild Coating-Kataloge** (ADR 0019): eigenes Format `raytatouille-coatings`, eigenes Schema, strikter Parser in C++, Fehler als `CoatingCatalogError` mit Datei und JSON-Pointer, in Python als gleichnamige Ausnahme.

Entscheidungen des Maintainers in #321 (2026-11-21):
1. Die Helfer geben ein **ganzes `rt.System`** zurück.
2. Der **Bildabstand ist eine Pflichtangabe**; kein paraxialer Solve im Helfer (das bleibt bei O1).
3. Der **Loader liegt in C++ in `rtt-io`** und wird in Python gebunden; eigenes JSON-Schema.
4. Vor dem Code kommt dieser ADR zur Freigabe.

## Entscheidung

### 1. Modul `raytatouille.design`

Neues Python-Modul `rt.design` mit den drei Helfern und dem Katalog (Punkt 3). Die Helfer bauen das Modell als dict in Dateiform (nur die nötigen Schlüssel, wie in einer handgeschriebenen Datei; nicht die vollständige Bearbeitungsform aus ADR 0024) mit `schema_version` = `rt.SCHEMA_VERSION`. Diese Konstante legt die Bindung neu an (`model::kSchemaVersion`), damit ein Sprung der Version (Regel 9) die Helfer nicht bricht. Das Ergebnis ist `System.from_json(json.dumps(...))`. Die Helfer rechnen nichts außer Summen von Abständen. Sie prüfen das System mit `rt.validate`: Fehler werfen `rt.DesignError` (neu, `RaytatouilleError` und `ValueError`, mit `diagnostics` wie `CompileError`), Warnungen gehen als `RaytatouilleWarning` weiter.

Gemeinsame Schlüsselwortargumente (alle Längen in mm, Wellenlängen in µm, Felder in Grad, Konventionen aus `docs/architecture.md`):

| Argument | Pflicht | Bedeutung |
| --- | --- | --- |
| `epd` | ja | Durchmesser der Eintrittspupille (`aperture: {type: epd}`) |
| `image_distance` | ja | Abstand vom Scheitel der letzten Fläche zur Bildebene (Detektor `image` mit Fläche `IMG`) |
| `stop_distance` | genau eines von beiden | Blendenknoten `stop` mit Fläche `STO` bei z = 0, die erste Linse um diesen Abstand dahinter; muss > 0 sein, denn ein Strahl aus der Blendenebene trifft eine Fläche im Abstand 0 nicht (AGENTS.md, #151, #177) |
| `stop_surface` | genau eines von beiden | Id einer Linsenfläche (z. B. `"L2.S1"`): Blende über `aperture.stop` (ADR 0039) ohne eigenen Knoten, die erste Linse bei z = 0 |
| `stop_radius` | bei `stop_surface` ja, sonst `epd/2` | Radius der kreisförmigen Apertur von `STO` bzw. der Blendenfläche; für eine Blende vor der ersten Linse ist `epd/2` die Eintrittspupille selbst, für eine Blendenfläche gibt es keine physikalisch sinnvolle Vorgabe |
| `semi_diameter` | nein, keine | Radius der kreisförmigen Apertur auf jeder Linsenfläche außer der Blendenfläche |
| `fields_y` | nein, `(0.0,)` | Feldwinkel y in Grad (`fields.points`, Typ `angle_deg`) |
| `wavelengths` | nein, `(0.4861, 0.5876, 0.6563)` | Wellenlängen in µm |
| `reference` | nein, `1` | Index der Referenzwellenlänge, 0-basiert (Vorgabe: 0.5876) |
| `name` | nein, `"Singlet"`, `"Doublet"` bzw. `"Triplet"` | Name des Systems |

Die Helfer:
- `singlet(radii, thickness, material, **gemeinsam)`: `radii` = (R1, R2), eine Linse `L1` mit den Flächen `L1.S1`, `L1.S2`.
- `doublet(radii, thicknesses, materials, **gemeinsam)`: verkittet; `radii` = (R1, R2, R3), `thicknesses` = (t1, t2), `materials` = (Glas 1, Glas 2); eine Linse `L1` mit drei Flächen und der Materialliste je Segment (ADR 0017).
- `triplet(radii, thicknesses, gaps, materials, **gemeinsam)`: drei Einzellinsen `L1` bis `L3` mit Luftabständen; `radii` 6 Werte, `thicknesses` 3, `gaps` 2 (Scheitel der hinteren Fläche zum Scheitel der nächsten Linse), `materials` 3.

Ein Radius `None` ist plan: Die Fläche bekommt keine `shape`. Radien folgen der Vorzeichenkonvention (Krümmungsmittelpunkt in +z: positiv), 0 ist ein Fehler. Materialien sind Referenzen `KATALOG:NAME` wie im Systemformat; ein Helfer mit einem Material schreibt einen Text, einer mit mehreren Segmenten eine Liste. Die Materialien werden erst beim Kompilieren aufgelöst.

**Lagen** (Summen in Python-`float`, Reihenfolge verbindlich, weil sie die Bits bestimmt):
- Knoten der ersten Linse: z₁ = `stop_distance` bzw. 0.
- Flächen relativ zu ihrem Knoten: 0, t1, (t1 + t2); die erste Fläche ohne `pose`.
- Knoten der nächsten Linse: z_{k+1} = z_k + e_k + g_k, mit e_k der relativen Lage der letzten Fläche von Linse k und g_k dem Luftabstand, von links nach rechts summiert.
- Detektor: z_img = z_last + (e_last + `image_distance`), also relativ zum letzten Linsenknoten wie die Flächen.

Mit dieser Regel treffen alle drei Referenzdateien bitgenau: 5.0 + (4.0 + 97.363) = 106.363, 5.0 + ((6.0 + 3.0) + 96.614) = 110.614, 16.488 + (3.127 + 41.10346) = 60.71846. Die Summe von links nach rechts ergäbe beim Triplet 60.71845999999999.

Asphären, Konik, Neigungen, Beschichtungen und luftgetrennte Dubletts gehören nicht zu v1 (Regel 1); wer sie braucht, ändert das Ergebnis mit `rt.apply_patch`.

### 2. Linsenkatalog: Format `raytatouille-lenses`

Eine Katalogdatei, Schema `schema/raytatouille-lenses.schema.json`:

```json
{
  "format": "raytatouille-lenses", "schema_version": "0.1.0", "catalog": "DEMO",
  "lenses": [
    {"name": "PCX-25-100", "kind": "singlet", "description": "plano-convex, f about 100 mm",
     "radii": [51.68, null], "thicknesses": [4.0], "materials": ["CONST:1.5168"],
     "diameter": 25.4}
  ]
}
```

- `kind` ist `singlet`, `doublet` (verkittet) oder `triplet`. Die Zahl der Einträge folgt der Art: `radii` 2, 3 bzw. 6; `thicknesses` 1, 2 bzw. 3; `materials` 1, 2 bzw. 3; `gaps` genau 2 beim Triplet und sonst nicht vorhanden (auch `"gaps": []` ist dann ein Fehler).
- `null` in `radii` ist plan; ein Radius 0 ist ein Fehler wie im Systemformat (`shape.radius_invalid`). Längen in mm, Radien mit Vorzeichen wie im Systemformat; Dicken > 0, Abstände ≥ 0.
- `materials` sind nicht leere Texte; ihre Form `KATALOG:NAME` prüft erst `MaterialLibrary` beim Kompilieren, wie bei den Schichten der Coating-Kataloge.
- `diameter` (optional, > 0) ist der freie Durchmesser jeder Fläche; `from_catalog` setzt daraus `semi_diameter = diameter / 2`.
- `description` ist optional.
- Katalog- und Linsennamen sind nicht leer und enthalten kein `:`; Linsennamen sind im Katalog eindeutig.
- Eine Blende enthält der Katalog nicht: Sie gehört zum System, nicht zur Linse (Frage 3).
- Strikter Parser wie für System- und Coating-Dateien (ADR 0008, 0020): unbekannte Schlüssel, falsche Typen und falsche Anzahlen sind Fehler mit Datei und JSON-Pointer. Das Schema beschreibt die Struktur einschließlich der Anzahlen je Art (if/then), der Grenzen und des Radius ≠ 0. Nur der Parser prüft: eindeutige Linsennamen, doppelte Schlüssel und Zahlen außerhalb von `double` (rtt-json). Die Beschreibung des Schemas sagt das wie bei `raytatouille-coatings`.

Herstellerdaten kommen nicht ins Repository. Die Testdatei `tests/catalogs/lenses/demo.json` enthält ausgedachte Namen mit den Daten der drei Referenzsysteme.

### 3. Loader in `rtt-io`

Neuer öffentlicher Header `rtt/io/lens_catalog.hpp` in `rtt-io` (die eigene Bibliothek dieses Auftrags; Regel 8 berührt das nicht), Quelle `src/lens_catalog.cpp`, gebaut mit `rtt-json` wie der Coating-Parser. `rtt-io` braucht dafür weder `rtt-material` noch `rtt-coating`, die Materialien bleiben Texte. Skizze (Doxygen mit Einheiten und `@throws` wie bei `parse_coating_catalog`):

```cpp
namespace rtt::io {
inline constexpr std::string_view kLensCatalogFormat = "raytatouille-lenses";
inline constexpr std::string_view kLensCatalogSchemaVersion = "0.1.0";
enum class LensKind { Singlet, Doublet, Triplet };
struct LensEntry {
  std::string name;
  std::string description;
  LensKind kind = LensKind::Singlet;
  std::vector<std::optional<double>> radii;  // mm; nullopt = plano
  std::vector<double> thicknesses;           // mm
  std::vector<double> gaps;                  // mm; triplet only
  std::vector<std::string> materials;        // CATALOG:NAME
  std::optional<double> diameter;            // mm
  bool operator==(const LensEntry&) const = default;
};
struct LensCatalog { std::string name; std::vector<LensEntry> lenses; };
class LensCatalogError : public std::runtime_error { /* file(), pointer() wie CoatingCatalogError */ };
LensCatalog parse_lens_catalog(std::string_view json_text, const std::string& file = {});
LensCatalog load_lens_catalog(const std::filesystem::path& file);
}
```

Die Bindung legt `rt.design.LensCatalog`, `rt.design.LensEntry` (nur lesend, `kind` als Text) und `rt.design.load_lens_catalog(file)` an. Der Fehler wird in `errors.cpp` zur Python-Ausnahme `rt.LensCatalogError` (`RaytatouilleError`, `ValueError`) mit `file` und `pointer`, wie `CoatingCatalogError`.

Dazu kommt `rt.design.from_catalog(entry, **gemeinsam)`: Es ruft den Helfer der Art mit den Daten des Eintrags auf. `semi_diameter` kommt aus `diameter`, sofern nicht übergeben; der Systemname ist der Linsenname, sofern `name` nicht übergeben ist. Die Blende (`stop_distance` oder `stop_surface`) ist wie bei den Helfern Pflicht. Einen Schreiber für Kataloge gibt es in v1 nicht.

### 6. Abnahme

Alle Abnahmen 1 bis 3 vergleichen `to_json()` bytegleich mit der Datei:

1. **Singlet** gegen `tests/reference/m1/singlet_const.rtt.json`:
   `singlet((51.68, None), 4.0, "CONST:1.5168", epd=20.0, stop_distance=5.0, semi_diameter=12.7, fields_y=(0.0, 3.5, 5.0), image_distance=97.363, name="Plano-convex singlet f = 100 mm, constant index 1.5168")`.
2. **Dublett** gegen `tests/reference/m2/achromat.rtt.json` (Abnahme der Roadmap):
   `doublet((61.5, -35.2, -136.9), (6.0, 3.0), ("SCHOTT:N-BK7", "SCHOTT:F2"), epd=20.0, stop_distance=5.0, semi_diameter=12.7, fields_y=(0.0, 3.5, 5.0), image_distance=96.614, name="Cemented achromat N-BK7/F2, f about 100 mm")`.
3. **Triplet** gegen `tests/reference/m2/cooke_triplet_surface_stop.rtt.json` (ohne Blendenknoten, Apertur nur auf `L2.S1`):
   `triplet((23.713, 7331.288, -24.456, 21.896, 86.759, -20.4942), (4.831, 0.975, 3.127), (5.86, 4.822), ("SCHOTT:N-LAK9", "SCHOTT:N-SF5", "SCHOTT:N-LAK9"), epd=12.5, stop_surface="L2.S1", stop_radius=10.0, fields_y=(0.0, 14.0, 20.0), wavelengths=(0.4862661791313749, 0.587721870012617, 0.6564506940778654), image_distance=41.10346, name=<Name der Datei>)`.
   Der zweite Abstand steht dezimal als 4.822; aus der Differenz 16.488 − 10.691 − 0.975 ergäbe sich 4.821999999999999.
4. **Inhaltswächter:** Jedes der drei Systeme kompiliert, `rt.validate` meldet keinen Fehler, und ein Strahlbündel des Achsenfelds erreicht `IMG` mit Status `ALIVE`.
5. **Loader:** `demo.json` wird gelesen, und jeder Eintrag ergibt über `from_catalog` mit den Argumenten aus 1 bis 3 (einschließlich `name`) bytegleich dieselben Systeme. Fehlerfälle mit Pointer: falsches `format`, falsche `schema_version`, unbekannter Schlüssel, unbekannte `kind`, falsche Anzahl von `radii`, `thicknesses`, `gaps` oder `materials`, `gaps` bei Singlet oder Dublett, Radius 0, Dicke ≤ 0, Abstand < 0, doppelter Linsenname, `:` im Namen. Das Schema nimmt `demo.json` an und lehnt dieselben Strukturfehler ab (`tests/schema`).
6. **Helfer:** `ValueError` bei falscher Anzahl der Argumente, bei keiner oder beiden Blendenangaben, bei `stop_distance` ≤ 0, bei `stop_surface` ohne `stop_radius` oder mit unbekannter Id und bei Radius 0; `DesignError` mit Diagnosen bei Fehlern von `rt.validate`. mypy `--strict` mit beiden NumPy-Pins.

### 7. Folgen für Tests und Regeln

Bestehende Tests und Referenzwerte bleiben unverändert. `test_model_read.py` und die Bitvergleiche sind nicht betroffen. Das Systemformat ändert sich nicht (kein Sprung von `kSchemaVersion`, Regel 9 gilt nicht).

### 8. Fragen an den Maintainer

1. **Fehler als Ausnahme statt Diagnoseliste.** In #321 steht „Diagnosen wie beim Systemformat“. Vorschlag: wie bei den Coating-Katalogen (ADR 0019) eine Ausnahme `LensCatalogError` mit Datei und JSON-Pointer beim ersten Fehler, keine Liste von `model::Diagnostic` mit Codes in der Registry. Ein Katalog ist eine Eingabedatei ohne Warnungen; eine Liste lohnt erst, wenn es Warnungen gibt.
2. **Blende über zwei Argumente.** Vorschlag wie in Punkt 1: `stop_distance` (> 0) oder `stop_surface`, genau eines davon Pflicht, keine Vorgabe; `stop_radius` bei `stop_surface` Pflicht, sonst `epd/2`. Die Alternative wäre ein Argument `stop: float | str` mit einer positiven Vorgabe.
3. **Keine Blende im Katalog.** Vorschlag: Der Katalog beschreibt nur Linsen; die Blende gibt `from_catalog` wie bei den Helfern an.
4. **Dublett nur verkittet.** Vorschlag: `doublet` ist in v1 verkittet; ein luftgetrenntes Dublett kommt erst mit einem späteren Helfer.
5. **Dateinamen.** Vorschlag: keine feste Endung, wie bei den Coating-Katalogen (`tests/catalogs/coatings/demo.json`); erkannt wird das Format an `format`.

## Verworfen

- **Loader nur in Python:** C++-Werkzeuge (CLI, spätere GUI) könnten Kataloge nicht lesen (Entscheidung 3).
- **Helfer geben nur einen Linsenknoten zurück:** zwei Aufrufe für ein rechenbereites System und mehr API (Entscheidung 1).
- **Paraxialer Bildort ohne Angabe:** eine Rechnung im Helfer, deren Rundung die Bitgleichheit gefährdet; gehört zu O1 (Entscheidung 2).
- **Detektor relativ zur letzten Fläche, von links nach rechts summiert:** trifft beim Cooke-Triplet die Datei nicht bitgenau (60.71845999999999); die Lage relativ zum letzten Linsenknoten (Punkt 1) trifft alle drei Dateien.
- **Vorgabe `stop` = 0:** Blende und erste Fläche lägen in einer Ebene, und Strahlen aus der Blendenebene verfehlten die Fläche (#151, #177).
- **Brennweite oder Hersteller-Nummern im Katalog:** Die Brennweite folgt aus den Daten und dem Glas; Herstellerdaten bleiben draußen (#321).
- **Helfer in C++:** Die Roadmap verlangt Python; C++-Nutzer schreiben die Systemdatei.

## Folgen

- Neues Dateiformat mit eigener Version 0.1.0; das Systemformat bleibt bei 0.11.0.
- `rtt-io` bekommt einen öffentlichen Header mehr; `rtt-py` ein Modul und eine Ausnahme.
- Spätere Erweiterungen (Asphären im Katalog, luftgetrennte Dubletts, ein Schreiber, `rtt import` aus Katalogen) erhöhen die Katalogversion und bekommen einen Nachtrag.
