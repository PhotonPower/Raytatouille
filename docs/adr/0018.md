# ADR 0018: Python-Build-Abhängigkeiten über pyproject.toml statt vcpkg

**Status:** angenommen (2026-10-04)

## Kontext

AGENTS.md Regel 4 lässt neue Abhängigkeiten nur über `vcpkg.json` zu. Für das Python-Paket
`raytatouille` (#32, ADR 0002) braucht der Build nanobind und scikit-build-core, die Tests numpy,
pytest und mypy. Der vcpkg-Port `nanobind` (2.13.0 an unserer Baseline) hängt am Port `python3`:
vcpkg baut dafür CPython 3.12 aus den Quellen (ungecacht etwa 10 Minuten je OS und Preset). Die
Erweiterung würde dann gegen die Header und unter Windows gegen die Importbibliothek dieser
vcpkg-Python gebaut statt gegen den Interpreter, der pytest und numpy ausführt. Das legt das
Projekt auf eine Python-Version fest, und `FindPython` kann die falsche Python finden. Der
Koordinator hat im Auftrag des Maintainers in #32 entschieden.

## Entscheidung

1. **Ausnahme von Regel 4 nur für reine Python-Build- und Testwerkzeuge:** nanobind,
   scikit-build-core, numpy, pytest und mypy kommen aus PyPI. Build-Abhängigkeiten stehen in
   `pyproject.toml` (`build-system.requires`), alle zusammen gepinnt in
   `libs/rtt-py/tests/requirements.txt`. Neue Werkzeuge dieser Art brauchen dieselbe
   Lizenzprüfung wie vcpkg-Abhängigkeiten (ADR 0010) und einen Eintrag in diesem ADR.
2. **C++-Bibliotheken** (Eigen, nlohmann-json, oneTBB, Catch2, ...) kommen weiterhin nur über
   vcpkg; die Ausnahme gilt nicht für sie.
3. **Python** ist der Interpreter, der baut: CMake findet nanobind über
   `python -m nanobind --cmake_dir` dieses Interpreters (`libs/rtt-py/CMakeLists.txt`).

## Lizenzprüfung (ADR 0010)

Geprüft an den installierten Paketen (`*.dist-info`, Lizenztexte im Paket) am 04.10.2026:

| Paket | Version | Lizenz | Rolle |
| --- | --- | --- | --- |
| nanobind | 2.13.0 | BSD-3-Clause | Build; Code wird in `_core` gelinkt |
| robin-map (in nanobind, `ext/robin_map`) | wie nanobind | MIT | Build; Code wird in `_core` gelinkt |
| scikit-build-core | 1.1.1 | Apache-2.0 | Build-Backend, nicht im Paket |
| numpy | 2.2.6 (Python 3.10), 2.4.6 (Python 3.11), 2.5.3 | BSD-3-Clause AND 0BSD AND MIT AND Zlib AND CC0-1.0 | Laufzeit (Arrays), vom Nutzer installiert |
| pytest | 9.1.1 | MIT | nur Tests |
| mypy | 2.4.0 | MIT | nur Tests |

Alle sind mit MIT verträglich. nanobind und robin-map landen als Code in der Erweiterung; ein
späteres Binärpaket (Wheel auf PyPI) muss ihre Lizenztexte mitliefern (BSD-3, Klausel 2), ebenso
die der C++-Abhängigkeiten im Wheel: oneTBB (Apache-2.0; unter Windows `tbb12.dll`, unter Linux
statisch gelinkt), nlohmann-json (MIT) und Eigen (MPL-2.0).

## Verworfen

- **vcpkg-Port nanobind:** baut CPython aus den Quellen, legt auf Python 3.12 fest und riskiert
  die falsche Python bei `FindPython` (siehe Kontext).
- **nanobind als Git-Submodul:** Version und Lizenzprüfung wären an einem dritten Ort.

## Folgen

- Der Python-Build braucht `pip install -r libs/rtt-py/tests/requirements.txt` vor CMake.
- Die C++-Presets sind unverändert; nur `ci-linux-python` und `ci-windows-python` bauen das
  Paket (`RTT_BUILD_PYTHON=ON`).
- AGENTS.md Regel 4 verweist auf dieses ADR.

## Nachtrag (#33): matplotlib

`raytatouille.plot` (#33) zeichnet Analyseergebnisse mit matplotlib. matplotlib ist eine
optionale Laufzeitabhängigkeit (Paket-Extra `raytatouille[plot]`, Import erst in den
Plotfunktionen) und für die Tests in `libs/rtt-py/tests/requirements.txt` gepinnt: 3.10.9 für
Python 3.10, 3.11.2 ab Python 3.11 (matplotlib 3.11 verlangt Python ≥ 3.11). Der Koordinator hat
die optionale Abhängigkeit und die Pins in #33 entschieden.

**Lizenzausnahme:** Die Matplotlib License steht nicht in der Liste erlaubter Lizenzen von
ADR 0010 (MIT, BSD, Apache-2.0, BSL-1.0, MPL-2.0, LGPL dynamisch). Sie ist eine permissive,
PSF-basierte Lizenz ohne Copyleft und wird mit Freigabe des Koordinators im Auftrag des
Maintainers (#33) zugelassen, weil matplotlib nur optional ist, vom Nutzer installiert und
weder gelinkt noch mitgeliefert wird. Für eine nicht optionale oder mitgelieferte Verwendung
gilt diese Ausnahme nicht.

| Paket | Version | Lizenz | Rolle |
| --- | --- | --- | --- |
| matplotlib | 3.10.9 / 3.11.2 | Matplotlib License (PSF-basiert, Klassifikator „Python Software Foundation License“), BSD-kompatibel | optional zur Laufzeit (Plots) und in den Tests, vom Nutzer installiert, nicht im Wheel |

Geprüft am installierten Paket 3.11.2 (`*.dist-info`, Lizenztext und Klassifikator) am
04.10.2026; 3.10.9 trägt dieselbe Matplotlib License (Lizenz seit Version 1.3.0 unverändert, so
im Lizenztext von 3.11.2). Das matplotlib-Wheel bringt eigene Bestandteile mit (u. a. FreeType unter
„FTL OR GPL-2.0-or-later“, Qhull, Schriften unter OFL-1.1); da `raytatouille` matplotlib weder
linkt noch mitliefert, betrifft das nur die Weitergabe von matplotlib selbst. Die
Abhängigkeiten von matplotlib (contourpy, cycler, fonttools, kiwisolver, pillow, pyparsing,
python-dateutil, packaging) installiert pip mit; auch sie landen nicht im Wheel von
`raytatouille`.

## Nachtrag (#404, 2026-11-17): Wheels auf PyPI

**Anlass:** Der Maintainer will `raytatouille` auf PyPI veröffentlichen, zuerst als Probe auf TestPyPI (#404). Die erste Version auf PyPI ist 0.10.0 aus main (Entscheidung in #404); der Tag `v0.9.0` enthält den Workflow nicht.

- **Workflow** `.github/workflows/release.yml`:
  - Wheels mit cibuildwheel für CPython 3.10–3.14 auf Linux x86-64 (manylinux_2_28), Windows x64 und macOS arm64. macOS hat die Mindestversion 26.0 (ADR 0047), also den Wheel-Tag `macosx_26_0_arm64`. Builds für free-threaded Python und musllinux gibt es nicht.
  - Dazu ein sdist ohne `tests/catalogs/`: Dort liegen Auszüge aus Herstellerkatalogen für die Tests, und ADR 0010 liefert Kataloge nicht mit (Entscheidung des Maintainers in #404). Der Job prüft das.
  - Die C++-Abhängigkeiten kommen aus vcpkg am Pin der CI. `tools/check_pins.py` prüft `VCPKG_COMMIT` jetzt auch in `release.yml`.
  - Die Auswahl der Builds, die Tests und die Reparatur stehen in `pyproject.toml` (`[tool.cibuildwheel]`). vcpkg, `CMAKE_ARGS` und unter Linux der Schritt `before-all` und der Binär-Cache kommen nur aus dem Workflow.
  - Jedes Wheel wird mit den Python-Tests aus dem Quellbaum geprüft, wie der Smoke-Test der CI. Python 3.14 läuft sonst in keinem CI-Job; dieser Test ist dort die einzige Prüfung. Die Testwerkzeuge kommen hier nicht aus `libs/rtt-py/tests/requirements.txt`, dessen genaue NumPy-Pins die CI nur unter 3.10 und 3.13 prüft, sondern aus `test-requires`: pytest gepinnt, NumPy, matplotlib und jsonschema mit Untergrenzen.
  - Windows: delvewheel liefert `msvcp140.dll` mit; `tbb12.dll` liegt schon neben `_core` im Paket und ist für delvewheel ausgenommen (es durchsucht das Wheel nicht). `_core` und `tbb12.dll` sind gegen die DLL-Laufzeit gebaut, CPython bringt nur `vcruntime140*.dll` mit; ohne das VC++-Redistributable schlüge der Import fehl.
- **Upload:** Trusted Publishing (OIDC) mit `pypa/gh-action-pypi-publish`, ohne Token. Die Umgebungen `testpypi` und `pypi` gehören je zu einem Publisher auf test.pypi.org bzw. pypi.org.
  - Ausgelöst wird von Hand mit dem Ziel `none`, `testpypi` oder `pypi`; PyPI nur von einem Tag `v<version>`, den der Job „Version“ gegen `pyproject.toml` prüft.
  - Diese Prüfung steht in der Workflow-Datei des gewählten Refs und lässt sich mit Schreibrechten umgehen. Den eigentlichen Schutz gibt die Umgebung `pypi` in den Repository-Einstellungen: nur Tags `v*` als Deployment-Ref und der Maintainer als Pflicht-Reviewer. Das richtet der Maintainer ein, zusammen mit den Publishern.
  - Änderungen am Workflow, an `pyproject.toml` oder an `LICENSES/` bauen und testen die Wheels im PR, ohne Upload.
- **Lizenzen der eingebetteten Bestandteile** (Abschnitt „Lizenzprüfung“ oben):
  - Die Texte liegen in `LICENSES/` (Übersicht `LICENSES/README.md`) und stehen über `license-files` in jedem Wheel unter `dist-info/licenses/`. Das sind oneTBB (Apache-2.0), Eigen (MPL-2.0), nlohmann-json (MIT) samt den eigenen Hinweisen von Grisu2 (F. Loitsch) und dem UTF-8-Decoder (B. Hoehrmann), pocketfft (BSD-3-Clause), nanobind (BSD-3-Clause) und das darin enthaltene robin-map (MIT).
  - Die Texte liegen im Repository statt beim Build gesammelt: nanobind liefert den Text von robin-map nicht mit, und so sind sie unabhängig vom Layout von vcpkg prüfbar.
  - `license` in `pyproject.toml` ist jetzt der SPDX-Ausdruck des Wheels: `MIT AND Apache-2.0 AND BSD-3-Clause AND MPL-2.0`.
- **Neue Werkzeuge** (nur im Workflow, nicht im Paket), geprüft am 17.11.2026 über die Lizenzangabe der GitHub-Repositories:

| Werkzeug | Version | Lizenz | Rolle |
| --- | --- | --- | --- |
| cibuildwheel | 4.3.5 | BSD-2-Clause | baut und testet die Wheels |
| delvewheel, auditwheel, delocate (von cibuildwheel installiert) | gepinnt von cibuildwheel | MIT, MIT, BSD-2-Clause | reparieren die Wheels (Windows, Linux, macOS) |
| build | 1.6.1 | MIT | baut das sdist |
| pypa/gh-action-pypi-publish | 1.14.3 | BSD-3-Clause | Upload über Trusted Publishing |
| actions/upload-artifact, download-artifact | v4 | MIT | Übergabe der Dateien zwischen den Jobs |

## Nachtrag (#406, 2026-11-18): NumPy-Pin für Python 3.11

numpy 2.5 verlangt Python ≥ 3.12. Unter Python 3.11 ließ sich `libs/rtt-py/tests/requirements.txt`
deshalb nicht installieren. Es gibt jetzt drei Zeilen: 2.2.6 für 3.10, 2.4.6 für 3.11 (die letzte
Reihe, die 3.11 noch unterstützt) und 2.5.3 ab 3.12. Die Lizenz von 2.4.6 ist dieselbe wie oben
(`License-Expression` im installierten Paket, geprüft am 18.11.2026). matplotlib 3.11.2 läuft ab 3.11
und bleibt.

Die CI testet weiter nur 3.10 und 3.13 (Entscheidung des Maintainers in #406). Wer die Pins ändert,
prüft den Pin für 3.11 lokal mit pytest (über ctest) und `mypy --strict`; die Wheel-Tests aus
`release.yml` laufen unter 3.11, aber mit `test-requires` statt dieser Datei.
