# ADR 0004: Parallelität mit oneTBB

**Status:** angenommen (2026-10-04)

## Entscheidung

`tbb::parallel_for` mit `static_partitioner` über Strahl-Batches. Feste Zerlegung und keine Reduktion in unbestimmter Reihenfolge, damit Ergebnisse deterministisch bleiben. Wird mit M1 als Abhängigkeit aufgenommen.

## Verworfen

OpenMP (uneinheitlich unter MSVC); eigene Thread-Pools.

## Nachtrag (#83, 2026-10-08): Zerlegung mit Abbruch und Fortschritt

Mit einem aktiven `RunControl` (`rtt/trace/run_control.hpp`) zerlegt der Tracer den Batch nicht mehr mit `static_partitioner` in etwa einen Block je Thread, sondern mit `simple_partitioner` in Blöcke von höchstens `block_size` Strahlen (Standard 256).
- **Warum:** Die Abbruchanfrage wird vor jedem Block geprüft. Mit einem Block je Thread käme der Abbruch erst nach etwa der ganzen Rechnung an. Mit 256 Strahlen läuft nach der Anfrage höchstens ein kurzer Block je Worker weiter, bei typischen Linsen deutlich unter einer Millisekunde.
- **Blockgröße 256:** Abwägung zwischen Latenz und Overhead. Je Block fallen eine Flag-Prüfung und eine atomare Addition an, gegenüber 256 Strahlverfolgungen vernachlässigbar. Kleinere Blöcke kosten Overhead, ohne dass eine GUI die kürzere Latenz merkt.
- **Determinismus bleibt:** Jeder Strahl wird unabhängig genau einmal und mit demselben Code gerechnet, und es gibt keine Reduktion über Strahlen in unbestimmter Reihenfolge. Das Ergebnis hängt daher weder von der Blockgröße noch von der Thread-Anzahl ab. Ein Test prüft das mit zwei Blockgrößen (256 und 7) und 1 bzw. 4 Threads bitgleich.
- **Ohne `RunControl`** (oder mit leerem) bleibt die bisherige Zerlegung mit `static_partitioner` unverändert.
- **Abgrenzung:** Abbruch und Fortschritt sind Laufzeitsteuerung, kein Teil der Rechnung. Sie gehören deshalb nie in die Options-Structs der Analysen, sondern sind ein eigener letzter Parameter in Überladungen.
