# ADR 0028: Relative Platzierung (Pose.reference, Pose.order)

**Status:** angenommen (2026-10-09)

## Kontext

Heute ist jede Pose absolut im Koordinatensystem (KS) ihres Elternknotens: eine Fläche im KS ihres Elements, ein Element im KS seiner Baugruppe. Eine Luftdicke zwischen zwei Elementen ist damit kein Parameter. Wird sie geändert, müssen alle folgenden Elemente einzeln verschoben werden. Für die Optimierung (M5) soll eine Dicke eine einzige Variable sein, und die Folgeelemente sollen mitwandern, wie in Programmen mit Flächentabelle. Das soll auch direkt hinter einem Faltspiegel gelten.

**Vorbild:** QUADOA-Handbuch V 24.08, Kap. 6.3 und 6.4 (relative Platzierung) sowie Kap. 6.6 (Reihenfolge von Drehung und Verschiebung). Nur als Vorbild genannt; nichts daraus steht im Repository.

**Ist-Stand:**
- `rtt::model::Pose` (`rtt/model/pose.hpp`): `position` und `rotation_deg` als `Param`, `pivot` als Zahl.
- `to_isometry(pose)` ergibt die Abbildung Kind → Eltern: p_Eltern = position + pivot + R·(p_Kind − pivot) mit R = Rx·Ry·Rz intrinsisch (Konventionen in `docs/architecture.md`). Erst wird verschoben, dann um den Pivot im KS des Kindes gedreht.
- compile setzt die globalen Transformationen in einem Lauf in Baumreihenfolge (Pre-Order) zusammen: global(Kind) = global(Eltern) · to_isometry(pose(Kind)) (`rtt-compile/src/compile.cpp`, `add_assembly`, `add_element`).

## Entscheidung

### 1. Zwei neue Felder an jeder Pose

Jede Pose (Baugruppe, Element, Fläche) bekommt zwei Felder. Im Modell kommen sie als letzte Felder mit Initialisierer, damit bestehende Aggregat-Initialisierungen gültig bleiben.

`reference` und `order` sind keine `Param`. Sie beschreiben die Struktur des Aufbaus, keine Zahl. Sie werden daher nicht optimiert und nicht je Konfiguration umgeschaltet (ADR 0029). Dasselbe gilt schon heute für `pivot`.

| Feld | Werte | Standard (im kanonischen Text weggelassen) | Modell |
| --- | --- | --- | --- |
| `reference` | `absolute`, `relative_to_preceding`, `relative_to_sibling` | `absolute` | `enum class PoseReference : std::uint8_t { Absolute, RelativeToPreceding, RelativeToSibling }`, `Pose::reference` |
| `order` | `translate_first`, `rotate_first` | `translate_first` | `enum class PoseOrder : std::uint8_t { TranslateFirst, RotateFirst }`, `Pose::order` |

### 2. Bezug: eine Regel für alle drei Arten

    global(X) = global(Bezug(X)) · to_isometry(pose(X))

- **`absolute`:** Bezug ist der Elternknoten, wie heute.
- **`relative_to_preceding`:** Bezug ist die letzte Fläche, die in Baumreihenfolge (Pre-Order) vor X steht, auch über Element- und Baugruppengrenzen hinweg. Für Fläche j > 0 eines Elements ist das Fläche j − 1 desselben Elements. Das KS der Bezugsfläche ist ihr eigenes, mit ihrer vollen Pose.
- **`relative_to_sibling`:** Bezug ist das vorangehende Geschwister in derselben Baugruppe bzw. demselben Element, in dessen eigenem KS. Für Flächen ist das dieselbe Fläche wie bei `relative_to_preceding`.
- **Zyklen sind unmöglich,** weil der Bezug immer früher in der Baumreihenfolge steht als X.
- Kinder eines relativ platzierten Knotens beziehen sich wie gewohnt auf ihn. Sie wandern also mit.

### 3. Reihenfolge von Drehung und Verschiebung

`to_isometry(pose)` hängt von `order` ab. t ist `position`, R die Drehung aus `rotation_deg`; das Ergebnis ist die Abbildung KS von X → KS des Bezugs.

- **`translate_first`** (heute, unverändert): p_Bezug = t + P + R·(p_X − P).
  - Erst wird um t im KS des Bezugs verschoben, dann um den Pivot P gedreht.
  - P ist **im KS von X** gegeben, wie heute.
- **`rotate_first`** (Koordinatensprung): p_Bezug = Q + R·(t + p_X − Q).
  - Erst wird das KS des Bezugs um den Pivot Q gedreht, dann um t längs der **gedrehten** Achsen verschoben.
  - Q ist **im KS des Bezugs** gegeben, weil die Drehung dort stattfindet, bevor das KS von X existiert.
  - Mit Q = 0 gilt p_Bezug = R·(t + p_X): `position` (0, 0, d) ist dann eine Dicke d längs der neuen z-Achse.
- **Gleichheit der Varianten:** Ohne Drehung sind beide gleich. Ohne Verschiebung und mit Pivot 0 ebenfalls.
- `order` gilt für **alle** Posen, absolute wie relative. Der Standard `translate_first` ist das heutige Verhalten; Dateien ohne das Feld bleiben bitgleich.
- **Umsetzung:** `to_isometry` baut für `rotate_first` die Abbildung aus dem vorhandenen Konstruktor `Isometry3(R, Q + R·(t − Q))`. `rtt-math` ändert sich nicht.
- **Erweiterungspunkt, nicht in M5:** Die Reihenfolge „erst z verschieben, dann drehen, dann x/y verschieben“ (im Vorbild „Z Pos XY“) kann später als dritter Wert von `order` dazukommen.

### 4. Koordinatensprung hinter einem Faltspiegel

Das KS einer Spiegelfläche ist ihr eigenes, gedreht wie der Spiegel. Es folgt nicht der reflektierten Achse. Mit `rotate_first` setzt das erste Element hinter dem Spiegel das KS auf die reflektierte Achse, und eine Dicke bleibt ein Parameter.

**Beispiel (Faltspiegel 45°):**
- **Aufbau:** Spiegel M bei z = 50 mm, Drehung (45°, 0, 0), eine Fläche M.S im Ursprung des Elements. Die Normale von M.S ist Rx(45°)·ẑ = (0; −0,7071; 0,7071). Licht längs +z verlässt den Spiegel längs +y, die reflektierte Achse ist die Gerade durch (0, 0, 50) in Richtung +y.
- **Linse L** mit `relative_to_preceding` (Bezug M.S) und `order` `rotate_first`: Drehung (−135°, 0, 0), Pivot 0, `position` (0, 0, 30).
  - Das gedrehte KS hat die z-Achse Rx(45°)·Rx(−135°)·ẑ = Rx(−90°)·ẑ = (0, 1, 0), also die reflektierte Achse in Lichtrichtung.
  - Der Ursprung von L liegt 30 mm darauf: global (0, 0, 50) + Rx(45°)·Rx(−135°)·(0, 0, 30) = (0, 0, 50) + 30·(0, 1, 0) = (0, 30, 50).
  - Mit Drehung (45°, 0, 0) läge z_L = −y. Dann gälte `position` (0, 0, −30), eine Dicke mit negativem Vorzeichen wie in Programmen, die hinter Spiegeln die z-Richtung umkehren. Gewählt ist hier z_L in Lichtrichtung.
- **Danach:** L2 mit `relative_to_preceding` (Bezug: letzte Fläche von L, 5 mm hinter dem Ursprung von L) und `position` (0, 0, d), Standard `translate_first`, liegt bei (0, 35 + d, 50). Für d = 20 also bei (0, 55, 50), für d = 25 bei (0, 60, 50): Die Dicke ist ein Parameter, und alles danach wandert mit.
- **Zum Vergleich, warum es das Feld braucht:**
  - Mit `translate_first` liegt die Verschiebung im KS des Bezugs, also längs der Spiegelnormalen. Drehung (−135°, 0, 0) mit `position` (0, 0, 30) ergäbe den Ursprung (0; −21,21; 71,21), neben der Achse.
  - Auf die Achse käme L nur mit einer Drehung um den Spiegelscheitel: Pivot (0, 0, −30) im KS von L und `position` (0, 0, 30). Die Dicke stünde dann zweimal in der Pose und wäre kein einzelner Parameter mehr.
- Alle Zahlen sind mit denselben Formeln nachgerechnet (Python).
- **Test** (mit #163): Trace des relativ platzierten Aufbaus gleich dem absoluten Gegenstück, die Transformationen auf eine vorab hergeleitete Toleranz der Komposition.

### 5. Prüfungen in validate

Alle mit Pointer auf `…/pose/reference`:
- `pose.relative_first_surface`: Die erste Fläche eines Elements ist relativ platziert (beide Arten). Ihr Bezug läge außerhalb des Elements, und das KS des Elements wäre dann bedeutungslos. Für Fläche 0 mit `relative_to_sibling` ist das die einzige Diagnose, nicht zusätzlich `pose.no_sibling`: eine Diagnose je Ort.
- `pose.no_preceding`: `relative_to_preceding`, aber vor X steht in Baumreihenfolge keine Fläche (z. B. das erste Element des Systems oder die Wurzel).
- `pose.no_sibling`: `relative_to_sibling`, aber X ist das erste Kind (oder die Wurzel).

`order` braucht keine eigene Prüfung: Beide Werte sind für jede Pose gültig.

### 6. Wirkung auf die übrigen Teile

- **compile:** Es führt den Bezug im bestehenden Pre-Order-Lauf mit, also die globale Transformation der zuletzt gesetzten Fläche und je Ebene die des vorangehenden Geschwisters. Für `absolute` mit `translate_first` bleibt der Rechenweg wörtlich derselbe (global(Eltern) · to_isometry(pose)). Systeme ohne die neuen Felder sind daher bitgleich.
- **Kristallachse und Achsen idealer Elemente:** Sie liegen weiter im KS ihres Elements (ADR 0026, Punkt 2) und folgen damit dessen Pose, wie immer sie zustande kommt.
- **Paraxial und Symmetrieprüfung:** unverändert. Sie lesen die globalen Transformationen der kompilierten Flächen.
- **Ghosts und Rückwege:** keine Wirkung. Die Geometrie hängt an der Baumreihenfolge, nicht am Pfad; ein Rückweg durch dieselben Flächen sieht dieselben Posen.
- **Bearbeitungsform und Undo (ADR 0024):** `reference` und `order` sind gewöhnliche Felder. Ein Patch nur auf eines davon verschiebt das Objekt, weil sich Bezug oder Reihenfolge ändern, die Zahlen aber nicht. Das ist gewollt.
- **GUI:** Verschieben im Baum ändert den Vorgänger und damit die Lage relativ platzierter Knoten. Für das Ziehen in 3D liefert `rt.layout.reference_frame` (#169) das KS des Bezugs, in dem die Pose gilt.
- **Toleranzen (M7):** Der Pivot ist bei `rotate_first` ein Punkt im KS des Bezugs, bei `translate_first` einer im KS des Knotens. Eine Kipptoleranz um den Pivot muss das berücksichtigen.

### 7. Format und Migration

- Beide Felder kommen mit dem gemeinsamen Schema-Sprung von M5 auf 0.4.0 (#162), zusammen mit ADR 0029 und 0030.
- **Migration 0.3 → 0.4:** Ein fehlendes `reference` ist `absolute`, ein fehlendes `order` ist `translate_first`. Ergebnisse bleiben bitgleich.

### 8. Grenze

- Ein Element, das relativ zu einem Vorgänger außerhalb der eigenen Baugruppe platziert ist, folgt der Pose dieser Baugruppe nicht: Sein Bezug ist die Fläche, nicht der Elternknoten.
- Wird die Baugruppe als Ganzes verschoben oder verkippt, bleibt das Element am Vorgänger.
- Für Toleranzen von Baugruppen (M7) kommt deshalb eine weitere Art von `reference` hinzu, „absolut, z relativ“, die das KS des Elternknotens mit dem z des Vorgängers verbindet.

## Verworfen

- **Nur Ort (Verschiebung relativ, Drehung absolut):** Hinter einem gekippten Element läge die Verschiebung im falschen KS, und eine verkippte Gruppe ließe sich nicht als Ganzes relativ fortsetzen.
- **Automatisch der reflektierten Achse folgen:** Das KS hinter einem Spiegel hinge vom Pfad ab (welche Fläche reflektiert, welche bricht). Die Geometrie wäre dann nicht mehr eine Eigenschaft des Aufbaus, und Ghosts, Rückwege und Layout sähen verschiedene Lagen.
- **Koordinatensprung als Sonderregel nur für relative Posen:** Die Bedeutung von `position` hinge dann vom Bezug ab. Mit dem eigenen Feld `order` ist sie an jeder Pose ablesbar, und auch eine absolute Pose kann einen Koordinatensprung beschreiben.
- **Faltung nur mit Pivot (`translate_first`):** möglich, aber die Dicke stünde in `position` und `pivot` (Punkt 4) und wäre kein einzelner Parameter.
- **Bezug über Namen** (z. B. `"relative_to": "L1.S2"`): beliebige Bezüge mit Zyklenprüfung, schwerer zu bearbeiten, und das Verschieben im Baum würde Bezüge brechen. Die zwei Arten decken die Flächentabelle und gruppierte Aufbauten ab.
- **Dicke als eigenes Feld statt einer Pose:** wäre ein zweiter Weg zur Lage und gälte nur für die z-Richtung. Die relative Pose enthält die Dicke als `position[2]`.

## Folgen

**Header-Änderungen** (Regel 8; dieser ADR ist die Begründung):
- `rtt-model`: `pose.hpp` (`PoseReference`, `PoseOrder`, `Pose::reference`, `Pose::order`, Doxygen von `to_isometry` mit beiden Reihenfolgen), validate (die Codes aus Punkt 5).
- `rtt-diagnostics`: die drei Codes in der Registry, jeder mit Testfall (ADR 0022).
- `rtt-io`: Leser, kanonischer Schreiber und Bearbeitungsform (#162).
- `rtt-compile`: keine Änderung an öffentlichen Typen. Die Auswertung (#163) ändert nur den Lauf in `compile.cpp`.
- `rtt-math`: unverändert.
- `rtt-py`: `Pose.reference` und `Pose.order` in `raytatouille.model` (#162).

**Umsetzung in eigenen PRs:**
- #162: Format 0.4.0 mit Modell, `to_isometry` für beide Reihenfolgen, Leser, Schreiber, Schema, Migration und Referenzdateien. `to_isometry` ruft für `translate_first` unverändert `Isometry3::from_pose` auf und hat nur für `rotate_first` einen eigenen Zweig. So hängt die Bitgleichheit nicht an einem für beide Reihenfolgen gemeinsamen Ausdruck;
- #163: Auswertung der Bezüge in compile mit den Referenzfällen;
- #169: `rt.layout.reference_frame`.

**Abnahme (#162, #163):**
- `to_isometry` mit `rotate_first` gegen die Formel aus Punkt 3, auch mit Pivot ≠ 0 (#162).
- Alle Referenzsysteme ohne die neuen Felder bitgleich.
- Jedes Referenzsystem im Test auf relative Posen umgeschrieben (Dicken statt Orte): dieselben globalen Transformationen auf eine vorab hergeleitete Toleranz.
- Der Faltspiegel aus Punkt 4, mit `rotate_first`.
- Der Kristall `m4/calcite_walkoff` relativ platziert: Achse und Walk-off unverändert.
- Das Ghost-Ranking eines relativ platzierten Systems gleich dem absoluten Gegenstück.
